## 2. 运行架构

```text
洛奇网络流量
  -> Npcap + 随包 mabicat.exe
  -> 本机 WebSocket（自动端口）
  -> live.py：接收 / 记录 raw / 音频调度
  -> AlertEngine（alerting.py）：状态机与时间判断
  -> 普通语音队列、红球独立队列、激光独立队列
  -> Windows 音频播放
```

### MicoPunch 共存

两者可能竞争 Npcap/后端资源。面向用户的固定说明是：**先启动本工具，再启动 MicoPunch**。若先启动 MicoPunch，本工具应弹窗提醒，而不是静默退出。

使用 UU 加速器时，说明书要求切换至路由模式。网络捕获失败、连接反复断开时，需同时询问加速器、Npcap、MicoPunch 与启动顺序。

## 4. 日志与排查规范

### 日志结构

V1.24e 起，每次启动建立：

```text
程序文件\BuffWatcher\logs\YYYYMMDD-HHMMSS-启动日志\
  launcher.log / console.log / launcher-status.log
  *-buffwatcher-raw.ndjson.gz
  *-buffwatcher-alerts.ndjson
  launcher-update.log（如本次执行了更新）
```

- `raw.ndjson.gz`：原始网络事件，查 ID、真实状态、实体与时序的根本依据。
- `alerts.ndjson`：规则判定、计划播报、实际发声、延迟和抑制原因；查“提前/延后/没播/误播”优先看它。
- `launcher.log` / `console.log`：后台启动、WebSocket 断连、MicoPunch 冲突、更新启动等。
- `%TEMP%\nogi-broadcaster-update.log`：仅更新器自身的替换过程。

向用户索要日志时，应要求压缩**整个本次启动目录**，并附：版本号、现实时间点、期望与实际播报、是否使用加速器、是否并开 MicoPunch、相关设置截图。Raw 日志可能包含游戏事件信息，不应在公开场合随意传播。

### 常见诊断路径

- 显示已连接但无声音：先核对是否已经用魔法盾识别到 self ID，再看 raw 是否有事件、alerts 是否已生成、音频文件是否存在。
- `WinError 10061` / WebSocket disconnected：本机后端端口被拒绝，先查 launcher/console 日志、Npcap、杀毒、加速器与 MicoPunch 启动顺序；它不是单凭截图即可断定的“更新失败”。
- 提醒时间偏差：先比对 `AlertAtLocal`、`EmittedAtLocal`、`TimingSource`、`State.EndAtLocal` 与 raw 中相应的 EventId 4/5。

## 5. 身份识别与时间模型

### Self ID

现行策略只使用玩家快速开关**魔法盾**时的自施加事件学习 self ID，学习窗口为 3 秒。不要重新引入“任意自 BUFF”或“周围玩家 BUFF”作为自我识别依据，否则会把队友乐曲、药水等串到自己身上。

小窗口状态含义：

- 红色 X「等待游戏数据」：Mabicat 仍在运行，但尚未收到用于开放本地 WebSocket 的游戏数据；不会因为等待超过 20 秒而被主动杀掉。此状态不要求玩家移动或操作技能。
- 橙色 O「请开关魔法盾」：已连接但未识别 self ID。
- 绿色勾「播报已启用」：已通过魔法盾识别 self ID。

魔法盾只负责启动后的单次 self ID 确认，不是在线状态检查或周期性心跳。后端等待游戏数据时不得提示玩家反复开关魔法盾。

没有游戏事件属于正常安静状态，不会触发 WebSocket 重连或 Mabicat 重启。只有进程退出、WebSocket 关闭或真实 socket/协议错误才进入恢复流程；恢复 Mabicat 时保留已经确认的 self ID。

### 时间来源的优先级

1. 有稳定 `SDUR` / `DUR` 的状态优先用它，例如状态支援。
2. 有已验证固定时长的状态用 `duration_seconds` 从应用包计时，例如生命的温度、负载转移等。
3. 药水存在 30/60/120 分钟版本，必须从应用包的 SBT/剩余量识别实际版本，不能硬编码 30 分钟。
4. 乐曲类没有可靠固定时长，只能用 `SBT - MCAGT` 加动态校准。该类提醒仍可能有随机偏移，设置页必须保留橙色风险说明。
5. 真实 `EventId=5` 移除用于结束确认；续 BUFF、同类自身覆盖、死亡批量清除须经过独立抑制逻辑，不能一概立即播报。

## 6. 已实现提醒：重要规则速查

### 玩家 BUFF

- 乐曲：战争序曲 `680`、活跃曲 `192`、行进曲 `193`。默认剩余提醒 20 秒；剩余提醒音只报名称；结束音报“名称 结束”。
- 徒安之歌 `1124`：乐曲结束瞬间或剩余提醒后用于判断三倍续时。若结束瞬间存在徒安，抑制原曲结束；同曲自我刷新在 12 秒内再施加则静默。不同乐曲互相覆盖仍应播报原曲结束。
- 乐曲强提醒：总开关控制三首曲；首次剩余提醒前加高频“滴滴滴”，5 秒后仍没有徒安则重复，直到有徒安或乐曲正式结束。
- 状态支援 `515`（关联 `511/512/513`）：优先 `SDUR/DUR`，不是靠通用 SBT；剩余 30 秒与结束提醒。
- 活力之歌 `800`（关联 `393`）、生命的温度 `874`、圣域之主 `1061`、负载转移 `1123`、净化之浪 `645`、各药水、坚定意志/逆光剑/致命穿透/超越生命等均在默认配置中。
- 星辰交汇：魔法 `1045`、物理 `1016`、炼金 `1046`，仅结束提醒、默认关闭，播报“占星”。
- 魔法盾 `59`：关闭播报“魔法盾关闭”。漏开提醒只在关键 Boss 战中启用且默认关闭；死亡时必须静默，复活后重新按用户设置的延迟判断。
- 魔法阵 `10133`、半神化 `78`、第三只眼：结束/冷却提醒走独立区块。魔法阵以本人 `SkillId 10103 / EventId 12` 作为冷却锚点，固定 E12 后 140 秒提示“**魔法阵 就绪**”，设置页不允许修改时长。本人型 E12 的 `TargetId` 为空并伴随 `10133/10138/10137`，地面目标型的 `TargetId` 非空且本人身上没有这些 buff，但二者的技能 ID 和本人施法者 ID 相同，因此不能依赖目标或 buff 决定冷却。第三只眼以首次开始信号作为冷却锚点，默认开始后 300 秒提示“**三眼 就绪**”；设置页可下拉选择 240 秒（特殊装备）或 300 秒（无特殊装备），结束/刷新信号不会推迟该时间。
- 托亚灵震爆：进度 StatId `198`，95% 时播报“托亚灵震爆 即将发生”。

### 死亡与续 BUFF

- 玩家死亡会导致多个 BUFF 同时移除；用 `EventId=15` 结合短时间多状态移除抑制一串结束播报。
- 不能只以 HP=0 判死亡：`deadly` 状态可能表现为极低/零 HP 但玩家未真正死亡。应结合受伤、死亡事件、批量移除来判断。
- 收到自身 `EventId=15` 后，服务端仍可能持续上报死亡前最后一个正数 HP。这个数值是陈旧快照，
  不能因为 `HP > 0` 就认定复活；当前实现记录死亡时 HP，至少等待 1 秒，并要求后续 HP 相对该快照
  真实变化 5 点以上，才恢复存活状态并重新按配置延迟检查魔法盾。死亡期间收到的魔法盾状态快照
  也不得单独解除死亡状态。

## 7. 关键敌人 DEBUFF

适用目标：布本 1/2/3/4 王（布 1 两阶段实体均算）以及凯莱赫 1/2 阶段。Boss 识别以最大 HP 指纹为主，不能依赖每场会变化的实体 ID。

### 上齐提醒与续期提醒必须分离

- “DEBUFF 上齐提醒”：需满足数值门槛；默认关闭。门槛可配置：物理破保 >= 30、魔法破保 >= 41、死亡锁定增伤 >= 61、兔子 >= 4 层。
- “破防 DEBUFF 续期提醒”：只看被监控 DEBUFF 是否存在并接近到期，**不看数值是否达到上齐门槛**；默认开启、30 秒。
- Boss 换阶段/实体替换时，不把旧实体的状态移除当成过期提醒；等待新实体重新上齐。
- 水泡 `CC598` 是无期限状态，不能因为没有正常结束时刻而造成开局误提醒。

### 已确认映射

| 含义 | CCID / 字段 | 说明 |
| --- | --- | --- |
| 魔法保护减少 | `1165` | 魔法破保数值见 `MCDMDPV` / `MCDMDTPV`。 |
| 物理保护减少 | `1164` | 物理破保数值见 `MCDDPV` / `MCDDTPV`。 |
| 死亡锁定增伤 | `426` + 必须存在的 `DAMAGE_BONUS` | 唯一允许进入上齐、续期和视觉 HUD 追踪的死亡锁定信号；数值门槛由用户配置，可低于 60。 |
| 牵引吸怪（非死亡锁定增伤） | `1166` | 吸怪附属效果；在事件路由层硬排除，不得参与任何死亡锁定追踪。 |
| 兔子 | `1138` + `MCCSSC` | 层数；`MCCSSCR` 为增伤数额。 |
| 卡丁车水泡 | `598` | 无期限，至 Boss 死亡/战斗结束。 |
| 枪手之眼 | `1122` | 不参与“上齐”；独立剩余/结束提醒，默认关闭、剩余 5 秒。 |

猫存在物理猫/勇敢猫与魔法猫/聪明猫两套等效 ID，逻辑应视作同一项满足条件；不要只识别其中一种。

当前 HP 读取 `StatId=28`，最大 HP 读取 `StatId=30`。提醒规则必须按“跨过阈值”触发，不要求严格等于。

### 布四安全屋

- 战斗起点：布四 Boss 最大 HP `3,449,779,200` 出现。
- 初始按 63 秒节奏计时；默认在安全屋前 7 秒播报“安全屋”，第一波静默。
- 后续只使用安全屋候选窗口内的真实实体重同步：`StatId=28/30 = 69,906,070`，相邻间隔 61--64 秒。必须排除同 HP 但来自固定血量机制的实体。
- 如果 Boss 战结束、退出副本或 Boss 实体消失，安全屋定时器必须停止。

### 布三红球

红球起点定义为：Boss 起手、红球在画面中出现的同一时刻。

- 高于 60% HP：约 15 秒后爆炸，处理阈值为 8 次有效接触。
- 低于/等于 60% HP：约 20 秒后爆炸，处理阈值为 10 次有效接触。
- 接触伤害使用 `SkillId=52407` 统计。注意玩家有“生命的帷幕”等护盾时可能不掉真实 HP，不能用伤害数值为零排除接触。
- 现实现使用起手、血量阶段、接触次数和时间窗的启发式判定：危险时走独立音频队列播放“危险红球，5，4，3，2，1，0”；达到安全接触阈值后停止余下倒数并播放确认过的清脆成功音。
- 红球实体出生/删除信号均不够稳定，不能作为唯一安全判断。该功能是经验规则，必须继续以视频 + raw 日志校验漏报与误报。

### 布三/布四激光（测试功能）

- 共同起手候选：`Op=0xafe7` / `SkillId=52401`；默认关闭。
- 预警“激光 四 三 二 一 零”使用独立队列，目标为实际伤害落在“零”。
- 星尘实体被摧毁时终止剩余播报；玩家无敌、免伤或伤害为零不应被误判为“激光取消”。
- 当前只能较可靠地进行起手预警，布四单发/双重激光尚无可靠提前区分方案；设置页不再显示“请勿过度依赖”提示。

### 压制机制研究

布三 30% / 布四 35% 的压制绿条与 CC/实体事件已有样本，但尚未得到足以解释“绿条速度由何决定”的可靠因果模型。不要把玩家攻击次数、伤害、宠物、成功防御人数等假设当作已证实结论；后续需要视频与同时段 raw 精确对齐继续取证。

## 9. 音频与界面

- 默认中文人声由 Azure `zh-CN-Xiaoxiao:DragonHDFlashLatestNeural` 生成，偏温和沉静、速度高于初版但避免过快失真。
- 语音资源默认目录：`assets/audio/xiaoyi`。
- 红球和激光提供试听及自定义音源入口；普通提醒仍按普通队列顺序播报，红球/激光具有独立播放队列，避免普通 BUFF 抢占关键倒数。

## 10. 已知限制与工作原则

1. 乐曲提醒不可能保证 100% 精确，SBT 本身存在波动；必须保留设置页的橙色风险说明，且任何新算法都要用大量历史 raw 回放验证。
2. 真实移除不总等于“应播放结束”：死亡批量清除、同曲自续、徒安续曲、Boss 换实体都需单独语义判断。
3. 游戏对象实体 ID 会变化，Boss 应优先按最大 HP/组合事件指纹识别。
4. 红球与激光属于高风险机制：功能更新前至少要做 raw 回放、覆盖成功/失败/战斗提前结束样本，并尽可能让用户用视频核验。
5. 每次新增设置字段都必须同步：默认 JSON、迁移逻辑、设置页加载/保存、构建后的发布包；否则用户打开设置页保存会丢字段。
6. 版本发布前必须确认：启动器可启动、设置页可打开、`latest.json` 版本正确、ZIP 内没有作者本地设置/密钥、更新后 `package-info.json` 在内部目录。
